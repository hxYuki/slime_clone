Rust 与 WESL 的 Uniform 契约

Shader 不知道窗口有多宽。要使用动态 aspect_ratio，CPU 必须把它写入 uniform buffer，WESL 再从绑定资源中读取。

本课胜利条件：给 material 增加一个参数时，知道 Rust 和 WESL 两侧必须同步修改什么。

1. 同一段数据，两种类型描述

Rust / CPU

#[derive(ShaderType)]
struct RegionColorScreenMaterial {
    rects: [Vec4; 32],
    color: Vec4,
    rect_count: u32,
    _padding: Vec3,
}

WESL / GPU

struct RegionColorScreenMaterial {
    rects: array<vec4<f32>, 32>,
    color: vec4<f32>,
    rect_count: u32,
    _padding: vec3<f32>,
}

它们不是自动共享的源代码。Rust 侧负责把值编码成 GPU 可读的数据；WESL 侧负责解释这些数据。字段顺序与对应类型必须兼容。

2. 增加 Aspect Ratio

Rust / CPU

rect_count: u32,
aspect_ratio: f32,
_padding: Vec2,

WESL / GPU

rect_count: u32,
aspect_ratio: f32,
_padding: vec2<f32>,

这里把尾部组织为 u32 + f32 + vec2。两侧同步后，Rust 系统还必须写入实际值：

screen_material.aspect_ratio = viewport_width / viewport_height;

关键边界：#[derive(ShaderType)] 会帮助 Rust 正确编码数据，但不会自动修改 WESL struct，也不会自动计算业务值。结构同步与数值更新仍由项目代码负责。

4. 当前项目只改 WESL 会发生什么？

使用 Encase 0.12 对当前两种结构计算出的实际偏移如下：

旧 Rust Layout · 560 bytes

rect_count  @ 528
隐式空洞    @ 532..544
_padding   @ 544

新 WESL Layout · 544 bytes

rect_count   @ 528
aspect_ratio @ 532
_padding     @ 536

所以新 WESL 的 aspect_ratio 会读取旧布局偏移 532..536 的隐式空洞，而不是旧 _padding.x。本例中旧 Rust buffer 更大，因此不会越界；但读到的值不属于有效业务契约。反方向若 shader 需要的布局大于实际绑定范围，通常会在管线或绑定验证阶段失败。
